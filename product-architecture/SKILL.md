# 功能架构设计文档

> 定位：产品设计文档（业务侧）→ 技术方案（技术侧）的**第一次翻译**。
> 只做**技术侧**：架构风格、技术选型、服务/模块划分、表定义、组件树、开发规范。**不重复**描述页面字段的业务含义——引用产品设计文档即可；**不新增或改名业务功能**。

项目路径与技术栈优先读取项目根 `product-workflow.json`；下文路径为默认示例，详见 `product-workflow/references/project-config.md`。

## 1. 何时使用

- 用户要定功能架构、做总体技术方案、选技术栈。
- 用户要从产品设计文档推导系统分层、模块划分、表结构、组件树。
- 用户要统一 API 命名规范、数据库迁移规范。
- 需要为下游（模块详细设计）提供输入。

## 2. 工作流程（五段，顺序执行）

| 段 | 动作 | 产出 |
|---|---|---|
| 1 | **需求说明文档解读与分析** | 核心需求提炼 / 用户故事 / 功能模块拆解 |
| 2 | **总体技术方案** | 架构风格、后端、前端、数据库、关键中间件/服务 → **系统架构 Mermaid 图** |
| 3 | **开发规范** | 核心原则、API 设计规范、数据库迁移规范 |
| 4 | **功能设计** | 后端模块设计与测试规划、**表定义 + ER 图**、前端组件化设计与测试规划 |
| 5 | **方案自检与总结** | 覆盖度检查、风险与假设 |

**输入**：`项目战术执行/00_产品设计文档.md`
**输出**：`项目战术执行/00_功能架构设计文档.md`

## 3. 硬规则

1. **对外接口统一 camelCase** —— 所有 API 的请求/响应字段一律 camelCase，不得出现 snake_case。
2. **DB 列 snake_case** —— 数据库字段一律 snake_case；与 API 的 camelCase 之间由后端序列化层转换。
3. **前端组件与页面文件 PascalCase**；样式文件 kebab-case；工具函数 camelCase。
4. **Mermaid 图规范** —— 所有架构图/ER 图遵守 `product-workflow/references/mermaid-guide.md`：用 `graph TD` / `graph LR`，**不用 `flowchart`**；节点文字禁止全角标点与括号；子图不使用 `direction`。
5. **功能清单以产品设计文档为准** —— 架构不得新增、删除或改名业务功能。若发现产品设计有疏漏，回到 `product-design` 修正，而不是在架构文档里"顺手补上"。
6. **技术栈基线（全族统一，勿自行变更）** —— 前端 React 18 + TypeScript + Vite + React Router v6 + **Ant Design 主线**；状态管理 Zustand / Redux Toolkit；后端 FastAPI + SQLAlchemy + PostgreSQL。除非用户在项目层面明确指定其它栈。

## 5. 门禁自检清单

**先说清哪些是脚本查的、哪些靠人工** —— 别把「人工守则」误当成「门禁」：

| 自检项 | 承担者 |
|---|---|
| 至少 1 张**真实** Mermaid 图 | `A1`（脚本 FAIL） |
| Mermaid 语法自检（无全角 / 无 `flowchart` / 无 `subgraph direction`） | `A2`（脚本 FAIL） |
| 每张表有字段定义表，且列头含 字段名·类型·约束·描述 | `A3`（脚本 FAIL） |
| 每张表有**表级**「索引」行（无索引须显式写 `索引 : 无`） | `A3`（脚本 FAIL） |
| 前端组件树里的组件/页面文件命名 PascalCase | `A4`（脚本 FAIL） |
| 每个功能都有归属 / 未新增改名业务功能 | `A5`（脚本 FAIL，**有限静态检查**：页面清单 ↔ 架构文档的集合比对） |
| ER 图与表定义一致 | `A6`（脚本 WARN，**弱检查**：仅比表名集合，关系与基数无法判定） |
| 对外 API 字段全 camelCase / DB 列全 snake_case | **人工**（机器难以可靠区分「接口契约区」与「表定义区」，强上会误报） |
| 字段定义表里每格内容是否写全（类型 / 可空性 / 默认值 / 约束 / 描述） | **人工**（脚本只验列头在不在，不验每格写得对不对） |
| 未重复描述页面字段的业务含义 | **人工**（语义判断） |

> **表定义口径（已统一；此前有过一版不一致，已收敛）**
> - 字段定义表固定 **4 列**：`字段名 / 数据类型 / 约束 / 描述`。字段级的「注释」**并入「描述」**。
> - **「索引」是表级信息，不是字段的属性** —— 与 `表名 / 所属模块 / 核心职责` 并列，单独一行 `索引 : ...`。不要塞进字段表，否则每行都要重复写一遍索引。无索引时显式写「索引 : 无」。
> - 旧自检清单曾要求「字段名 / 类型 / 是否必填 / 默认值 / 约束 / 索引 / 注释」**七项**，与规范正文和样例的 4 列冲突（承担者表里还写成 6 项），已按上述口径收敛。
> - 注意 **模块详细设计**里的 DDL 是另一层：索引与注释在那里本来就以 `PRIMARY KEY` / `CREATE INDEX` / `COMMENT` 的形态存在（见 `product-module-design` 的 `M4`），两处不矛盾。

**自检清单**

- [ ] 产品设计文档中的**每个功能**都在架构中有归属（模块 / 表 / 组件）
- [ ] 存在至少 1 张**真实**系统架构 Mermaid 图
- [ ] 所有 Mermaid 图通过语法自检（无全角标点、无 `flowchart`、无 `subgraph direction`）
- [ ] 对外 API 字段全部 camelCase
- [ ] DB 列全部 snake_case
- [ ] 每张表有：表名 / 所属模块 / 核心职责 / 字段定义（`字段名 / 数据类型 / 约束 / 描述` 四列）/ 索引
- [ ] 「索引」写在**表级**单独一行（无索引时显式写 `索引 : 无`）
- [ ] ER 图与表定义一致（表名、关系、基数）
- [ ] 前端组件树覆盖所有页面，且组件与页面文件命名 PascalCase
- [ ] 未新增或改名业务功能
- [ ] 未重复描述页面字段的业务含义（只引用）
- [ ] 运行 `scripts/validate_arch_doc.py` 判定 PASS

```bash
python3 scripts/validate_arch_doc.py \
  --arch-doc   <项目根>/项目战术执行/00_功能架构设计文档.md \
  --design-doc <项目根>/项目战术执行/00_产品设计文档.md
```

> `--design-doc` 用于页面覆盖弱检查（把产品设计文档的「页面清单」与架构文档比对）；不传则跳过该项。

## 7. 与相邻阶段的边界

| 内容 | 归属 |
|---|---|
| 页面有哪些字段、字段的业务含义、交互规则 | `product-design` |
| 表有哪些列、列的类型与约束、系统怎么分层 | 本 skill |
| 单个模块的 API 请求/响应逐字段展开、伪代码、测试用例表 | `product-module-design` |
| 页面代码怎么实现 | `product-development` |

**判断口诀**：写「业务上要什么」→ 产品设计；写「系统上怎么装」→ 功能架构；写「这个模块具体长什么样」→ 模块详细设计。

## 结构门禁补充

缺少核心内容不能以 WARN 放行。使用完整技能包的 Mermaid 解析器检查语法；不适用的数据库/API/前端须按 `product-workflow/references/verification-contract.md` 写具体 N/A 理由。语法通过不证明业务语义或旧版渲染效果正确。
