# 问题诊断（只读）

> 定位：链路上的「体检医生」。**只出报告，不动手术。**
> **写入边界：不得修改需求、设计、代码或测试实现。** 允许新建诊断报告、在既有 `90_诊断报告_<主题>.md` 文末追加诊断/复核记录，以及维护 `.product-workflow/issues.json` 问题台账。不得删改历史证据，不得把“尚未验证”写成“已解决”。修复动作回到对应阶段执行；用户已明确授权修复时按授权范围继续。

## 1. 何时使用

- 阶段检查未通过，但原因不明确。
- 产物之间对不上（如架构文档漏了产品设计里的功能、API 契约前后不一致）。
- E2E 用例持续失败且不知是产品缺陷还是用例问题。
- 用户直接问"这段设计/代码有什么问题""帮我排查一下"。

**不适用**：已经明确知道要改什么——那不需要诊断，直接回对应阶段 skill。

## 2. 诊断维度

| 维度 | 检查什么 |
|---|---|
| **产物链路** | 上一阶段产物是否真的被下一阶段消费？产物是否缺失/自相矛盾？**是否陈旧**？—— 跑 `product-workflow/scripts/check_freshness.py --project-root <项目根>` 判定，它会直接说明上游**变了什么**、该从哪个阶段重跑 |
| **契约一致性** | 产品设计的字段 ↔ 架构的表结构 ↔ 模块的 API 契约，三者是否对得上？命名是否 camelCase / snake_case 分层正确？ |
| **规范违背（脚本可查）** | 跑相关校验脚本，看是否违反可自动判定的硬规则（V2 排版约束、Mermaid 规范、每页 ≤2 表、AC 编号规则等）——**以脚本输出为准，不要凭印象** |
| **规范违背（人工核对）** | 脚本覆盖不到的写作守则。**重点是「字段规格只在一处出现」**：字段的类型/必填/校验是否只在「字段字典」里出现，还是被页面概述、数据流、或另一张表重复定义（`C5` 只能拦住"另起一张表"这种形态，散文里的重复它看不到） |
| **检查证据** | 相关校验脚本（如 `validate_design_doc.py`）的输出是什么？FAIL 项具体是哪些？ |
| **运行时证据** | 三层监控（控制台/网络/页面错误）快照、失败请求、数据库状态 |
| **环境与依赖** | 版本不一致、依赖冲突、环境变量缺失、容器构建问题 |

## 3. 工作方法

1. **先取证，后推断** —— 读取实际文件/日志，不靠推测。
2. **区分「现象」与「根因」** —— 例如"API 400"是现象，"前端提交了 snake_case 而契约要求 camelCase"才是根因。
3. **定位到阶段** —— 每个结论必须指向一个具体阶段（product-design / product-architecture / product-module-design / product-development / product-e2e-test），这样才知道该回哪。
4. **给出可执行建议，但不执行** —— 建议要具体到文件和改法。

## 4. 输出报告结构

**落盘路径**：`项目战术执行/90_诊断报告_<主题>.md`

- `<主题>` 用简短 kebab 或中文短语，如 `90_诊断报告_e2e-删除用例失败.md`
- 同一问题反复诊断时**追加到同一文件**（在文末加新的诊断段落），不要建一堆 `90_` 文件
- `90_` 前缀让它排在模块详细设计（`01_`…）之后，不干扰主链产物排序

```markdown
# 诊断报告：<问题一句话>
## 结论摘要
- 根因：<一句话>
- 归属阶段：product-xxx
- 严重级别：阻断 / 严重 / 一般 / 建议

## 现象
<观察到的客观事实，附文件路径与行号、日志片段>

## 根因分析
<从现象推导到根因的推理链，标注哪一步是推测>

## 影响面
<波及哪些产物、哪些下游阶段>

## 修复建议
1. <具体动作> → 应改文件：<路径>，建议改为：<内容>
2. ...

## 未确认项
<信息不足、需人工确认的部分，禁止凭猜测下结论>
```

## 5. 边界与禁止事项

- ❌ 不修改需求、设计、代码或测试实现；报告追加和台账维护遵循上方写入边界
- ✅ **只新建**诊断报告与修复建议清单（落 `项目战术执行/90_诊断报告_<主题>.md`）
- ❌ 不替用户做需求决策
- ❌ 不在证据不足时给确定结论——标注「推测」或列入「未确认项」

## 问题台账与结项

诊断后按 `product-workflow/references/verification-contract.md` 更新台账。每项记录 ID、负责人、级别、阻断属性、状态；关闭须提供带哈希的实际证据，接受风险须有真实人工确认。`待补充`、空白未确认章节和未知状态均不能视为解决。旧报告不删除，通过 `legacy_sources` 绑定原章节正文哈希和已关闭问题，保留可追溯的复核记录。
