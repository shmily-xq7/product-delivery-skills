# 产品交付图表规范

本规范决定“为什么画、画哪一种、必须表达什么”，并给出本 skill 自带的 Mermaid 语法基线。

## 1. 选择图型

| 阶段 | 图型标识 | 适用条件 | 必须表达 |
|---|---|---|---|
| 需求沟通 | `current-target-flow` | 旧流程改造或现状问题需要对齐 | 现状阻塞点、目标变化、范围边界 |
| 需求沟通 | `user-journey` | 多角色、多触点或跨渠道体验 | 角色、阶段、目标、关键触点、问题点 |
| 产品设计 | `business-flow` | 存在顺序、判断和异常路径 | 开始、主要动作、决策、异常、结束 |
| 产品设计 | `swimlane` | 两个及以上角色存在交接 | 角色泳道、动作归属、交接、系统回写 |
| 产品设计 | `state` | 一个业务对象有明确生命周期 | 初态、事件、条件、终态、非法或异常转换 |
| 产品设计 | `navigation` | 页面间跳转构成任务路径 | 页面、入口、跳转条件、返回或中断路径 |
| 功能架构 | `system-context` | 系统与用户或外部系统有边界 | 系统边界、外部参与者、主要交互方向 |
| 功能架构 | `deployment` | 有多环境、主机、容器或独立服务 | 运行区域、部署单元、连接、协议或端口 |
| 功能架构 | `data-flow` | 数据跨系统或跨安全边界流转 | 数据来源、处理、存储、去向、边界 |
| 功能架构 | `er` | 存在持久化实体及关系 | 实体、主外键、关系和基数 |
| 模块设计 | `sequence` | 多参与方调用、回调或异步消息 | 参与者、调用顺序、返回、失败、重试或超时 |
| 模块设计 | `module-dependency` | 模块依赖方向影响实现或发布 | 模块、依赖方向、共享依赖、循环风险 |
| 测试 | `test-coverage` | 关键路径包含多个 AC 或状态分支 | AC、对应测试、实际通过状态、未覆盖项 |
| 诊断 | `failure-sequence` | 故障跨组件传播 | 时间顺序、触发点、错误传播和观测证据 |
| 诊断 | `cause-tree` | 同一现象有多类候选原因 | 现象、原因层级、已证实/已排除/待验证状态 |
| 诊断 | `impact-map` | 变更或故障影响多个模块 | 起点、直接影响、间接影响、阻断程度 |
| 结项 | `delivery-overview` | 需要面向评审者说明最终交付关系 | 交付范围、主要模块、外部依赖和验证状态 |

`diagram_tool.py` 接受的 `--type` 值与本表一致。相同语法可以表达不同图型，但登记时必须写真实语义类型，不能全部标成 `business-flow`。

## 2. 阶段触发规则

- 图表按条件生成，不按阶段机械凑数。
- 产品设计至少保留现有业务流程 Mermaid 图；有多角色交接时改用或补充泳道表达。
- 架构文档已有系统架构和 ER 图要求；部署、数据流仅在系统条件适用时增加。
- 模块涉及三个及以上参与方、异步回调、重试、超时或补偿时，应提供时序图。
- 对象存在四个及以上业务状态，或存在禁止转换时，应提供状态图。
- 测试覆盖图只能读取真实 AC 与当前运行证据；没有执行结果时标记未知，不能推测通过。
- 诊断图必须绑定日志、错误记录或诊断报告中的证据，不把猜测画成既定事实。

## 3. 拆图规则

出现任一情况时拆成“总览 + 细节”：

- 一张图承担两个不同问题，例如同时解释部署位置和接口调用顺序。
- 主路径与异常路径交叉过多，读者无法沿单一方向阅读。
- 节点文字需要缩小才能容纳，或一个节点承载多段说明。
- 图中存在超过 15 个主要节点，或跨越超过 5 个角色/系统边界。

拆图后必须共享稳定的业务名词和 ID。总览允许聚合，细节图补全被聚合内容；不得把删除内容伪装成简化。

## 4. 语义自检

### 流程 / 泳道

- 每个动作使用“动词 + 宾语”。
- 决策写成可回答的问题，每个出口有条件标签。
- 每条路径最终到达结束、失败、取消或返回点。
- 泳道按真实责任划分，系统动作不归到人工角色。

### 状态

- 状态是持续条件，事件是触发变化的动作，两者不混写。
- 每条转换标明事件；存在条件时写清条件。
- 初态、成功终态和失败/取消终态清楚。
- 文档中的状态枚举、图和代码命名保持一致。

### 架构 / 部署 / 数据流

- 逻辑组件、运行单元和数据存储使用不同名称，不用一个框混代。
- 外部系统和信任边界明确。
- 连线方向有含义；双向关系不能用两个含糊箭头代替说明。
- 部署图只写已确定的环境和拓扑，不把候选方案画成最终方案。

### ER

- 实体名与表定义一致。
- 主键、外键、关系和基数可与 DDL 对账。
- 多对多关系有中间实体，不能只画抽象连线。

### 时序

- 时间从上到下，参与者从左到右保持稳定。
- 同步调用、异步消息和返回含义清楚。
- 关键失败、超时、重试和补偿与接口契约一致。
- 不把内部算法步骤伪装成跨参与者消息。

### 测试 / 诊断

- 测试覆盖图中的状态来自当前执行证据，不来自测试文件中的注释。
- 未覆盖、跳过、失败和未知分别表达。
- 原因树区分证实、排除和待验证；没有证据的节点不能标成根因。
- 影响图区分直接与间接影响，避免“全部受影响”的无效结论。

## 5. 文件与可访问性

- 图表 ID 使用大写字母、数字、连字符或下划线，长度 3–64，例如 `ORDER-STATE`。
- 标题描述主题，描述文本说明读者应理解的关系。
- SVG 必须包含 `role="img"`、`<title>` 和 `<desc>`。
- HTML 应包含 UTF-8 声明，不依赖远程资源；打印时保持白底可读。
- 颜色用于强调，不作为唯一状态编码；失败、未知等还需文字标签或不同线型。
- 中文标签优先使用系统中文字体，避免依赖在线字体。

## 6. Mermaid 语法基线

- 流程与架构关系使用 `graph TD` 或 `graph LR`；状态、时序和实体关系分别使用 `stateDiagram-v2`、`sequenceDiagram`、`erDiagram`。
- 不使用 `flowchart`，不在 `subgraph` 内声明 `direction`，保持与现有阶段检查规则一致。
- 节点文字使用半角括号和标点；包含空格或特殊字符时放入引号或方括号标签。
- 节点 ID 仅使用英文字母、数字和下划线，显示文字与 ID 分离。
- 一行只表达一个节点、关系或指令，避免把多条语句压在同一行。
- 先用最小子图验证语法，再逐段加入节点；渲染失败时保留原始报错，不以截图替代源码。

## 7. 交付判断

自动检查可以证明：来源块仍存在、哈希一致、产物未被修改、SVG/HTML 结构有效。

自动检查不能证明：业务语义完整、关系正确、视觉布局适合目标读者、测试真实通过。交付前仍需对照阶段文档目视复核。
