# 产品设计文档

> 定位：把模糊业务需求转成**可交付、可验收**的产品设计文档。
> 只做**业务侧**：业务流程、页面、字段、交互。**不碰**技术选型、表结构 DDL、服务分层、组件树——那是 `product-architecture` 的职责。

项目路径与技术栈优先读取项目根 `product-workflow.json`；下文路径为默认示例，详见 `product-workflow/references/project-config.md`。

## 1. 何时使用

- 用户要写/更新《产品设计文档》。
- 用户要写需求说明、做设计初始化大纲、拆功能清单。
- 用户要设计某个页面的字段规格、交互规则、页面清单。
- 需要为下游（功能架构设计）提供输入。

## 2. 前置子流程（按需，可单独调用）

三个阶段递进，可按实际成熟度从任一段切入：

```
① 需求说明 → ② 设计初始化大纲 → ③ 功能清单拆解 → ④ 产品设计文档（主体）
```

| 子阶段 | 参考 | 产出 | 落点 |
|---|---|---|---|
| ① 需求说明 | `references/requirement-spec.md` | 需求的概要描述 / 功能入口 / 页面设计 / 功能说明 | 见下，**前置章节** |
| ② 设计初始化 | `references/design-init.md` | 立项大纲（业务背景 → 现状分析 → 功能设计分析） | 见下，**前置章节**；**默认只输出模板骨架** |
| ③ 功能清单拆解 | `references/function-list-breakdown.md` | 可交付功能清单（分层：领域模块 → 子能力 → 工作单元） | 见下，**前置章节** |
| ④ 产品设计文档（主体） | `references/product-design-spec.md` | 业务流程 / 页面清单 / 功能设计详情 / 全局检查 | `项目战术执行/00_产品设计文档.md` |

**①②③ 不单独建文件** —— 它们的产出统一作为 `项目战术执行/00_产品设计文档.md` 的**前置章节**（见第 5 节结构）。理由：一条链路只产出一份文档，评审、移交与归档都只需看一个文件，避免出现 4 个"半个文档"。

前置章节**按需出现**：材料齐备就写全，不齐就留白或整章省略，**不设阶段检查**（校验脚本只检查主体章节）。范例 `references/sample-user-management.md` 的开头四章就是「② 设计初始化（版本 B）+ 主体」合并的实例，可直接对照。

原始需求统一取自 `项目战略规划/原始需求.md`。

## 3. 主体工作流（五步，逐步执行不可跳）

| 步 | 动作 | 产出 |
|---|---|---|
| 1 | **理解分析** | 提炼业务目标、用户角色、边界与不做什么 |
| 2 | **产品业务流程** | Mermaid `graph TD` 多角色流程图（遵守 `product-workflow/references/mermaid-guide.md`） |
| 3 | **页面清单** | 表格：页面名称 / 入口路径 / 核心功能 / 优先级 |
| 4 | **页面设计详情** | 每页/每弹窗：基本信息 → 页面概述 → 数据流 → 页面布局设计详情（ASCII）→ **字段字典** → **交互矩阵** → **验收标准（AC 编号）** |
| 5 | **全局检查** | 设计原则检查、优化建议、功能区分度检查 |

**逐步产出的意义**：第 2 步的业务流程是页面清单的依据，第 3 步的页面清单是第 4 步的目录。跳过任何一步都会导致「页面漏设计」或「设计与业务对不上」。

## 4. 强约束（V2 排版规则，必须遵守）

前三条是 V2 相对 V1 的核心改进，也是模型最容易违反的地方；第 4 条是「可验收性」的硬要求：

1. **按钮操作不单独成表** —— 操作按钮写在「交互矩阵」里，不要为按钮另起一张表。
2. **字段规格只在一处出现** —— 字段定义只在「字段字典」中完整列出；页面概述、数据流里只能引用字段名，不得重复定义。
3. **每个页面 / 弹窗尽量 ≤ 2 张表** —— 即「字段字典」+「交互矩阵」。超出说明你把并列信息拆错了层级。
4. **每个页面/弹窗必须有验收标准（AC）** —— 编号形如 `AC-USER-01`，2–8 位大写模块缩写 + 两位序号，**全文唯一**；用编号列表承载，**不要另开表格**（否则突破第 3 条）。编号规则与写法见 `references/product-design-spec.md` 第 6 节。

**哪些是脚本校验的、哪些靠人工** —— 别把「人工守则」误当成「阶段检查」：

| 规则 | 校验项 | 强度 |
|---|---|---|
| 按钮操作不单独成表 | `C4` | 脚本 FAIL（阻断） |
| 每个页面/弹窗 ≤2 张表 | `C5` | 脚本 FAIL（阻断） |
| 页面/弹窗必须含「验收标准」 | `C14` | 脚本 FAIL（阻断） |
| AC 编号格式合法 / 全文唯一 | `C12` / `C13` | 脚本 FAIL（阻断） |
| 页面/弹窗应有「字段字典」 | `C6` | 脚本 FAIL（须含实际表格内容） |
| **字段规格只在一处出现** | **——** | **纯人工核对，无脚本** |

> **关于第 2 条**：它**没有脚本校验**。原因是这条规则点名的场景是「页面概述、数据流里不得重复定义」——那是**散文**，要把「引用字段名」和「重复定义字段规格」可靠地区分开，正则做不到，强加检查只会大量误报。
> 唯一**间接**相关的是 `C5`：如果重复是以「另起一张表」的形式出现的，该作用域表数会超 2 而被拦住；但散文里的重复，`C5` 看不到。
> 所以这条靠**人工**执行：写完逐页扫一遍，确认字段的类型/必填/校验只出现在「字段字典」里，别处只提字段名。

**其他硬规则**
- 每个页面的 tab 页、弹窗、抽屉都**不能遗漏**，各自都要有布局图与字段/交互说明。
- 页面布局图（ASCII 线框）遵守 `product-prototype/references/ascii-ui-generator.md`：**用 ASCII 字符绘制、不混入 Unicode 框线、不用 emoji**（允许 `▼ □ ☑ ☐ ● ○` 等单宽几何符号做状态标记），行宽 ≤100 列、等宽对齐、标注区域标题与关键按钮。文件树 / 流程示意不受此限。
- 缺失信息做**最小合理假设**并显式标注「假设：」；不得沉默填充。
- 视觉规格（配色/字号/间距/组件形态）引用 `product-ui-spec`，不要在此文档另立一套。

## 5. 输出文档结构

```markdown
# <产品名称>设计文档

# 【前置章节 · 按需】①②③ 的产出并在这里，不单独建文件
#   标题随所选模板（见 references/design-init.md、
#   references/requirement-spec.md、references/function-list-breakdown.md）；
#   材料不足可整章省略。此段不参与阶段检查。

# 【主体章节 · 必需】以下四章需要通过阶段检查
## 业务流程            ← Mermaid 图，含异常分支
## 页面清单            ← 表格
## 功能设计详情
### <页面名称>
#### 基本信息          ← 页面标题、路径、入口
#### 页面概述          ← 目标定位、数据展示与用户操作
#### 数据流            ← 输入 / 处理 / 输出
#### 页面布局设计详情   ← ASCII 图 + 区域说明
#### 字段字典          ← 唯一字段定义处
#### 交互矩阵          ← 操作 × 前置条件 × 结果 × 异常
#### 弹窗/表单设计详情  ← 布局 + 字段字典 + 交互矩阵 + 验收标准（同上结构）
#### 验收标准          ← AC 编号列表，覆盖页面主体，全文唯一
## 全局检查            ← 设计原则检查结果 / 优化建议 / 功能区分度检查
```

**产出后必做：盖章** —— 运行 `product-workflow/scripts/check_freshness.py --stamp <本文档路径>`，在文档**开头**写入脚本生成的「生成元信息」块（记录它基于哪份 `原始需求.md`）。**不要手工删改这个块**：它是陈旧检测的依据——原始需求一变，本文档就会被判陈旧并触发全链回流。

**「验收标准」的位置与形态**：页面级放页面小节末尾；弹窗/抽屉/步骤/子 tab 各自在自己的小节内附一份。**用编号列表，不用表格**——写法和编号规则见 `references/product-design-spec.md` 第 6 节。

## 6. 阶段检查清单

产出后逐项确认，任一项不过即视为未完成：

- [ ] 文档含全部规定章节（业务流程 / 页面清单 / 功能设计详情 / 全局检查）
- [ ] 至少 1 个**真实** Mermaid 图（不是文字描述冒充）
- [ ] 每个页面/弹窗的字段定义**只在字段字典出现一次**（**人工核对**——此条无脚本校验，见第 4 节说明）
- [ ] 每个页面/弹窗的表格数 ≤ 2
- [ ] 没有「按钮操作单独成表」
- [ ] 每个 tab / 弹窗 / 抽屉都有布局图与字段+交互说明
- [ ] 每个页面/弹窗/步骤/tab 都有「验收标准」，条目带 `AC-<模块缩写>-<两位序号>` 编号
- [ ] AC 编号**全文唯一**，且每条都能写成一个测试断言（写不成断言说明没写到位）
- [ ] 缺失信息已用「假设：」显式标注
- [ ] 无技术选型、表结构 DDL、服务分层内容（越界内容移交架构阶段）
- [ ] 运行 `scripts/validate_design_doc.py` 判定 PASS

```bash
python3 scripts/validate_design_doc.py --doc <项目根>/项目战术执行/00_产品设计文档.md
python3 scripts/validate_design_doc.py --doc <...> --json   # 机读
```

## 7. 范例

`references/sample-user-management.md` 是一份**用本规范产出的完整范例**（用户管理模块），仅作为历史排版参考，不作为新任务的默认起点——但先读它顶部的「范例说明」：它的**排版是合规的**（页面主体 2 张表、每个弹窗各 2 张表），但成文早于 AC 体系，因此运行阶段检查时只剩 `C14`（全文无 AC 编号）一个 FAIL，属预期行为。

**AC 的写法样例**以 `references/product-design-spec.md` 的输出样例为准（`AC-USER-01` 起那一组），那份样例已按当前规范写全，可直接照抄结构。
