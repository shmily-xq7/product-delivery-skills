# 设计初始化 —— 立项大纲模板

> **选择指引**：本模板提供**两个版本**，按项目成熟度择一使用——
> **版本 A（增强版）**适用于有存量系统、需要先逐条盘点「现状 vs 诉求」的场景；
> **版本 B（精简版）**适用于全新功能、或需要一份更短立项提纲的场景。
> 两版章节结构不同，**不要混用**——选定后在整份文档内保持一致，便于人工对照与后续合并（**没有脚本校验这些标题**，一致性靠人工）。
>
> **用法**：用于产品设计的最前序——把模糊业务诉求转成一份结构化大纲，作为后续「功能清单拆解 → 产品设计文档」的输入。使用时**只输出模板骨架，不填充内容**（除非调用方明确要求直接成稿）。
> **落点**：产出并进 `项目战术执行/00_产品设计文档.md` 的**前置章节**（主体章节之前），**不单独建文件**；材料不足可整章省略。范例 `sample-user-management.md` 开头四章就是本文档「版本 B」并入后的实例。

---

## 版本 A · 增强版（推荐默认）

适用：需求相对复杂、存在存量系统、需要先盘点「现状」再谈设计。

```markdown
# 业务背景
## 业务诉求
[详细描述业务需求和目标]

## 概念解释
[关键概念和术语定义]

## 诉求梳理
- [诉求1]
- [诉求2]
- [诉求3]

# 现状分析
- [诉求1]
  - [子功能1]：
    功能现状：[已有功能 ✅ / 没有相关功能 ❌]
    数据现状：[数据情况描述]
  - [子功能2]：
    功能现状：[已有功能 ✅ / 没有相关功能 ❌]
    数据现状：[数据情况描述]
- [诉求2]
  功能现状：[已有功能 ✅ / 没有相关功能 ❌]
  数据现状：[数据情况描述]

# 功能设计分析
## 涉及的页面路径
[页面导航路径]

## 功能实现思路
[整体实现方案描述]

## 功能拆解
1、[功能拆解项1]
[具体实现描述]

2、[功能拆解项2]
[具体实现描述]

# 功能设计文档
```

**增强版的设计意图**：把「诉求」与「现状」逐条对照（✅/❌ 盘点），强制在动手设计前暴露存量差异——这是避免「重复建设」和「漏改旧逻辑」的关键动作。

## 版本 B · 精简版

适用：全新功能、无存量包袱，或需要一份更短的立项提纲。

```markdown
# 需求业务背景
## 业务诉求

## 概念说明

# 功能现状
## 功能当前状态

## 数据当前状态

# 功能梳理
## 功能实现思路
[总体的实现思路]

## 事项拆解
1、[事项1]
涉及页面路径：
事项描述：
2、[事项2]
涉及页面路径：
事项描述：

# 功能详细描述
```

## 输出要求

- **默认只输出模板骨架，不填充内容。**
- 若调用方要求成稿，则按所选版本的章节结构填充，并遵守 `product-requirement/references/expression-principles.md` 的表达规范。
- 缺信息处标注「假设：」或「⚠️ 待确认」，**禁止沉默填充**。
- 章节标题**建议保持稳定**，便于人工对照、以及后续合并进产品设计文档。
- **要说清一点**：**没有任何脚本会检查初始化大纲的章节**。`validate_design_doc.py` 只校验 `00_产品设计文档.md` 的「业务流程 / 页面清单 / 功能设计详情」三章，初始化大纲的章节不在其中。所以标题一致性靠人工保证，**别指望阶段检查拦住**。
