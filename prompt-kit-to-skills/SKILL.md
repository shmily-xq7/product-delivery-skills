# 提示词工具包 → skill 族

> 适用场景：用户手里有一套「AI 提示词 / 规范文档 / 角色定义 / 命令模板」的目录（常见于 Cursor 的 `.cursor/agents` + `.cursor/commands`、自建 prompt kit、设计规范库），希望变成能被 AI 助手自动检索并执行的 skill。
>
> 核心难点不是"抄写文件"，而是 **边界划分**（拆几个 skill）与 **冲突修复**（同一主题存在多个版本/多个技术栈）。这两点决定成败。

## 七步流程

### 第 1 步 · 清点（不要跳过）

```bash
find <kit_dir> -type d -maxdepth 2 | sort
wc -l $(find <kit_dir> -name "*.md") | sort -n     # 看体量分布
```

产出：**分组表**（每组文件数 + 总行数 + 一句话定位）。这一步就能看出 kit 的真实结构，往往和名字给的印象不同。

### 第 2 步 · 并行深读

用 Explore 子代理**并行**读（3 个上限，按组分工）。给每个代理的指令必须包含：

1. 逐文件回答：**用途 / 核心章节 / 产出什么交付物 / 引用了哪些其他文件 / 出现的强约束（原文摘录）**
2. **上下游依赖**：点明"A 是 B 的输入"这类链路
3. **冲突与重复清单**：逐字节重复？V1/V2 版本冲突？技术栈打架？
4. **分组建议**：哪些文件天然属于同一 skill，为什么

> 关键：让代理**报告差异**而不只是摘要。冲突信息比内容摘要值钱得多。

### 第 3 步 · 粒度决策（必须问用户）

先给出链路图，再让用户选。三种粒度：

| 方案 | 形态 | 适用 |
|---|---|---|
| **主控 + 阶段**（推荐） | 1 个编排 skill 定义流程/产物/门禁 + N 个阶段 skill + M 个横向支撑 skill | 链路长（≥4 阶段）、有明确上下游 |
| 阶段制 | 一个阶段一个 skill | 链路清晰但阶段彼此独立 |
| 合并制 | 2–5 个粗粒度 skill | 内容少、或用户不想管太多 skill |

同时必问：**技术栈覆盖范围**（多栈并存时保留哪些）、**安装位置**（用户级 vs 项目级）、**与已有 skill 的关系**。

### 第 4 步 · 资产映射表

一行一项，格式：`来源路径 → 目标 skill/references 路径 → 用途`。
**必须同时标注三类特殊项**：`【改写】`（内容需修改）、`【合并】`（多源合成一份）、`【不迁移】`（归档理由）。这张表就是执行清单。

### 第 5 步 · 冲突修复清单（问题 → 动作）

必查这 8 类，几乎每次都会命中：

| 类别 | 症状 | 动作 |
|---|---|---|
| 逐字节重复 | 同名不同前缀的两份文件内容相同 | 只取一份 |
| 版本冲突 | V1/V2 输出格式不兼容 | 二选一，旧的归档 |
| 技术栈打架 | 同一层出现两套选型（如 Tailwind vs AntD） | 定主线，另一套降为可选 |
| 绘图语言冲突 | 规范写 Mermaid、附件却是 PlantUML | 定默认，另一套标可选 |
| **硬编码绝对路径** | `/Users/<某人>/...` | 改为 CLI 入参或相对路径 |
| 命令路径漂移 | 命令引用的文件路径已不存在 | 改为实际路径 |
| 过时版本约束 | "xx v8.8 限制" | 泛化为版本无关，保留语义 |
| 残缺文件 | 内容不完整、只有几条外链 | 不迁移，记入清单 |

> **红线**：先出清单给用户判定，不要私自删源文件。修复只作用在**新建的 skill 副本**上。

### 第 6 步 · 撰写 SKILL.md

```yaml
---
name: <kebab-case，带族前缀便于聚合，如 product-xxx>
description: "<做什么 + 阶段标记 + 触发词列表 + 不负责什么>"
version: "1.0.0"
agent_created: true
---
```

**description 是整个族里最容易翻车的地方**——它是 skill 被自动检索匹配的**唯一依据**：

- 每个 description 必须含 **阶段标记**（"第 N 阶段"）或 **类别标记**（"横向工具"），便于人眼与模型区分
- 必须含 **触发词列表**，且各 skill 的触发词不得雷同
- 必须含 **"不负责…（那是 xxx）"** 边界句，明确把相近请求推给兄弟 skill
- 写完做一次**互查**：把全族 description 打出来并排看，凡两段读起来会混淆的就改

**正文只放**：何时使用 / 流程 / 硬规则 / 自检清单 / references 索引 / 与相邻阶段的边界。
**长规范正文一律进 `references/`**——SKILL.md 会被自动加载，references 是按需读取，不要把 600 行规范塞进 SKILL.md。

### 第 7 步 · 提取 assets 与交付校验

模板抽取用**行区间精确切**（先 `grep -n '^```'` 找围栏，再 `sed -n 'a,bp'`），并在文件头写清**来源与章节**，便于日后回溯。

交付前跑：

```bash
# 脚本语法
for f in <skill>/scripts/*.py; do python3 -m py_compile "$f" || echo FAIL $f; done
# 残留硬编码路径
grep -rn "/Users/[a-z]" <skills_dir>/<prefix>-*/
# 残留废弃技术栈
grep -rln "Pinia\|Vuex\|shadcn\|Tailwind" <skills_dir>/<prefix>-*/references/
# frontmatter 与 description 互查
for d in <prefix>-*/; do awk '/^name:|^description:/' "$d/SKILL.md"; done
# 清理空目录与 __pycache__
find <prefix>-*/ -type d -empty -delete
find . -name __pycache__ -type d -exec rm -rf {} +
```

### 第 8 步（按需）· 给规范加一条「可校验的硬约束」

规范里出现"必须…""应有…"这类要求时，先判断它是**真门禁**还是**口号门禁**：

| 强度 | 表现 | 判定 |
|---|---|---|
| 硬门禁 | 有脚本判定，FAIL → 非零退出码 → 真阻断 | 可用 |
| 软门禁 | 脚本只判 WARN，不阻断 | 半可用，靠人自觉 |
| **口号门禁** | 只写在门禁表里，**没有任何东西会去检查它** | **永远不产生"不过"的结果 = 写了等于没写** |

**口号门禁比"根本没写"更危险**：AI 读到以为有人核，人读以为脚本会挡，两边都不查 → 静默漏过。

要新建一条可校验约束（例如给文档加编号体系），按这 4 步：

1. **先确认"被检查的对象"存在**。若规范引用的概念在体系里根本没有（没有产生它的环节、没有格式定义、没有承载位置），那"实现它"就不是写个脚本，而是新增一整套子系统。**先问用户是否真要引入这个概念**，不要默默开工。
2. **定编号 / 格式规则并写成正则**。**纯 ASCII**（`AC-USER-01`）优于中文编号 —— 编号要进代码注释、要参与全局唯一校验。
3. **写校验器，造正负例自测**：格式错、重复、缺失、越界各造一份，确认能精确命中。
4. **接到门禁表 + 补样例**。规范自己的输出样例里**必须**出现新写法的示范，否则使用者不知道怎么写。

**十个必须注意的实现细节**（都踩过）：

- **统计必须按「作用域」分组，不能整段加总**。判定"每页 ≤2 张表"时，把"页面主体 + 所有弹窗"加总会得出 `2 + 2×N` 的假超标，**让每一份含弹窗的正常文档都被误判 FAIL**。正确做法：按"页面主体 + 各弹窗/抽屉/步骤/tab"分作用域统计。
- **元素识别只按后缀判定，不要用"包含即排除"的词表**。用「标题含『详情』就排除」会误杀 `查看用户详情弹窗`。改成 `endswith(弹窗/抽屉/tab)` 或 `startswith(步骤)`，既准确又简单。
- **跨 skill 引用写完整路径、放在同一对反引号内**。拆成 `` `skill-a` 的 `references/x.md` `` 会让引用检查器报"缺失"（识别不到 owner）。另外**检查器的正则要让 skill 名允许数字**——`product-e2e-test` 含 `2`，`[a-z-]+` 匹配不到它会假报。
- **同一个根因不要重复报**。例如"编号格式不合法"和"没有编号"是两个检查项，但前者命中时后者会跟着报，让报告翻倍变噪。后者应加条件跳过。
- **有的规则就是无法可靠脚本化，此时别硬凑**。典型是"规格只在一处出现""描述要准确"这类**散文约束**——正则无法把"引用"与"重复定义"可靠分开，强上检查必然大量误报。正确的处理是**明确标为人工核对项**，并写清"为什么不能脚本化 + 有没有间接的脚本兜底"，而不是：① 塞个不可靠的检查凑数；② 直接删掉规则本身（规则对产出质量仍有价值）。同理，一个文件里同时列"脚本可查项"与"人工核对项"时，**把两者分开成两张清单/表格**，避免读者把人工守则误当成门禁。
- **代码块与散文要用对版本**。找**代码块**（`CREATE TABLE`、`mermaid`、`tsc` 片段）必须用**带围栏的原文**定位，并记录行号——用去围栏后的文本去找，那一行早被删掉了，永远找不到；反过来做**散文类统计**（章节、表格数、字段规格列）必须用**去围栏后的文本**，否则 ASCII 线框里的 `|` 行会被当成表格分隔符。混用会出现"代码块查不到"和"表格凭空多出一堆"两种相反的错误。
- **「唯一性」规则的粒度要对**。「编号不得重复」这类规则若套到**整篇文档**，会全线误报——同一个编号在文档里合法地出现多次（原文引用段、汇总清单、多条用例各引用一次）。唯一性只能施加在**登记清单**这一层（例如"覆盖清单里同一编号只登记一次"）。**规则定错粒度比实现写错更隐蔽**，因为误报看起来像"文档真有问题"。
- **做「失效/陈旧检测」时，难点是灵敏度，不是能不能做**。用整文件哈希检测"上游改了、下游该重做"实现只要几行，但它对**任何**改动（含改错别字）都告警，而这条链最下游往往是**代码**——重跑代价很大。结果是告警疲劳，人开始无视门禁，比没有机制更糟。正确做法是**分层**：人写的自由文本类上游（需求）用整文件哈希（它变本就该重审全链），结构化产物之间用**契约指纹**（只对可提取的集合取哈希，如 AC 编号 / 页面名 / 表名 / 接口路径）——改错别字不动集合、不告警，集合变了才告警，灵敏度恰好等于"实质变更"且不需要人工纪律。另外**代码产物不要塞哈希**（污染源码），由"最近的陈旧上游"推导即可。
- **同族多个脚本的 `--json` 输出形状必须统一**（都用数组，或都用对象）。否则一旦有人写"聚合器"去汇总它们，形状不一致的那个会被**静默跳过**——而且症状是"未检测"，看起来像环境问题，不像自己的 bug。
- **在受限 PATH 的 shell 里执行外部命令，必须用绝对路径，且对管道产物做空值断言再提交**。真实事故：环境 PATH 连 `base64`/`tr`/`wc` 都没有，`B64=$(base64 < file | tr -d '\n')` 静默得到**空字符串**，随后的 GitHub Contents API PUT 把远端文件**写成了 0 字节**——命令还报了成功。防御三件套：① 外部命令一律绝对路径；② 编码/转换结果先断言非空（`[ -n "$B64" ] || exit`）；③ 远端写操作完成后**立即用独立通道拉回内容做哈希比对**，不能只看命令退出码。
- **"是否计入判定"的布尔标志极易写反，必须用"应该 FAIL 的场景"验证**。做"按范围裁剪结项条件"这类功能时，每个条件带一个 `counted` 标志（范围外不计入就绪）——写反了的症状是**双向静默**：该 FAIL 的场景被放过（范围该判的没判）、该 PASS 的场景被误伤（范围外恒真条件被计入）。只在"一切正常"的场景验证发现不了它，必须构造一个**该条件应当 FAIL 的负例**（如范围内产物缺失 / 该判的 AC 漂移），确认它真的变红。只验证 PASS 场景 = 只验证了一半。
- **审计"门禁强度不均"时，先问「这个阶段该不该有门禁」**。不是所有阶段都需要同等强度：只读分析角色不产出被消费的产物，本就不需要门禁；代码阶段的语言级检查（类型、lint、命名）天然属于 `tsc`/`eslint`，用脚本去 grep 源码是造轮子。正确的模型是「**一份产物一个校验器**」，而不是「每个阶段一个」。

> **最有效的自检**：拿**规范自己的输出样例**去跑校验器。如果规范样例过不了自家门禁、且并非有意为之，那就说明"规则与实现不一致"——这是最隐蔽的一类缺陷，往往意味着**校验器自己写错了**，而不是样例写错了。

## 已知陷阱

1. **别整包复制参考工程**。带 `node_modules` 的项目动辄上万文件，只提炼需要的那几份文本。
2. **别盲信"参考资料可提炼"**。计划里想从某个参考工程提炼样式/约定前，**先 grep 目标技术栈残留**（如 Element UI 的 `.el-button`、`#409eff`）。技术栈不一致时，提炼等于污染——应改为独立重建。
3. **范例可能与新规则冲突**。老范例按旧规范产出，跑新校验器可能 FAIL。处理方式：在范例文件顶部**显式注明这是预期行为**，并指出新文档应以什么为准。**但先排除校验器自身的 bug**——这类 FAIL 里混着真实违规和脚本误判，务必逐项确认（见第 8 步末条）。
4. **空目录会残留**。`mkdir` 了但没用上的目录（如计划里的 assets）记得 `find -type d -empty -delete`。
5. **旧资产的删除**。优先移入系统废纸篓（`mv <dir> ~/.Trash/<name>-<日期>`）而非 `rm`，效果等同移除工作环境但留回收退路；并明确告知用户。
6. **子代理也会写文件**。派发 Plan/Explore 子代理时明确"只做设计不要写文件"，否则可能覆盖你的计划文件。
7. **同一条消息里对同一文件连发两个编辑，会静默丢改动**。两个都返回"成功"，但第二个是在第一个改动**之前**的旧快照上计算的，结果被第一个覆盖——文件里只剩第一处。**同一文件的多次修改必须分开发送**，改完先确认落盘再改下一处。
8. **整段替换时，锚点必须从「行首」起到「行尾」止**。若 `old_string` 从一行**中间**开始或结束，替换会把新内容拼接进原行，并连带吞掉紧随其后的空行、`---` 分隔符与标题。这类破坏**不报错**，只有复查结构才能发现。→ 每轮收尾固定做一次「标题层级 + 行数」的结构核对。
