# 模块详细设计文档

> 定位：功能架构（系统级）→ 详细设计（模块级）的**落地翻译**。
> 一个模块产出一份文档，文件命名 `<序号>_<模块名>详细设计.md`（如 `01_用户管理模块详细设计.md`）。
> 产物落 `项目战术执行/<序号>_<模块名>详细设计.md`。

## 1. 何时使用

- 用户要写某个模块/页面的详细设计。
- 用户要把功能架构里的 API 契约**逐字段展开**、把表结构写成 DDL。
- 用户要设计某模块的组件拆分、状态管理、测试用例。
- 需要为下游（代码开发、E2E 测试）提供直接依据。

## 2. 依赖（前置条件，缺一不可）

| 输入 | 路径 | 用途 |
|---|---|---|
| 产品设计文档 | `项目战术执行/00_产品设计文档.md` | 提取本模块对应的**页面功能设计内容**（原文完整复制） |
| 功能架构设计文档 | `项目战术执行/00_功能架构设计文档.md` | 提取本模块的**代码结构、表定义、API 清单** |
| 页面设计规范 | 本 skill `references/module-design-spec.md` | 决定输出结构与命名规范 |

若上游缺失或内容明显不足以支撑本模块，**先回流上游补齐**，不要自己编造。

## 3. 输出结构（四大部分，顺序固定）

### 一、产品设计
从产品设计文档「功能设计详情」中**完整复制**本模块对应页面/功能的设计内容：

- **完整复制**，不省略、不简化、不改写。包括标题层级、表格、代码块、ASCII 图、列表编号。
- 覆盖：功能基本信息、功能概述、页面功能流程（Mermaid）、数据流（输入/处理/输出）、页面布局图（ASCII）、交互说明、弹窗/表单设计详情、**验收标准（AC 编号列表）**。
- **本模块覆盖的 AC**：单独列出本模块实现的所有验收标准编号（从产品设计文档各页面「验收标准」小节摘出），逐条注明由哪一部分设计承载（哪个页面/接口/校验）。这是「设计 → 模块 → 测试」三段对账的中间环节——**不得遗漏、不得自行新增**。

> 这一步的目的是让详细设计文档**自包含**——开发者不用来回翻两份文档。

### 二、前端详细设计
- **代码结构**：从功能架构的「前端代码结构树」中提取本模块相关文件，树形展示。
- **核心组件设计**：表格，含组件名 / 核心职责 / Props（名称·类型·必填·默认值·用途）/ 事件 / 插槽 / 其他依赖。
- **状态管理（Zustand / Redux Toolkit）**：State / Selectors / Actions。
- **核心实现逻辑（伪代码）**：覆盖数据获取、状态更新、错误处理、用户反馈、路由导航。

### 三、后端详细设计
- **代码结构设计**：从功能架构的「后端代码结构树」中提取本模块相关文件，树形展示。
- **数据库设计**：`CREATE TABLE` DDL（字段/类型/约束/索引/注释）+ **ER 图**（Mermaid `erDiagram`）。
- **API 接口设计**：逐接口的**契约表** —— 接口名 / Endpoint（方法+路径）/ 请求参数（Path·Query·Body）/ 成功响应（2xx + JSON 结构示例）/ 错误响应（400·403·404 等）。
- **核心实现逻辑（伪代码）**：校验、核心处理、数据持久化与事务、响应组装、异常处理。

### 四、测试详细设计
- **代码结构**：单测/集成/E2E 文件树。
- **核心实现逻辑（伪代码）**：E2E 关键场景（环境准备 → 用户动作模拟 → 状态校验 → 清理）。
- **测试用例设计**：表格 —— 用例 ID / **对应 AC 编号** / 测试层级（单元·集成·E2E）/ 测试目标 / 前置条件 / 测试步骤 / 预期结果。E2E 用例落地到 `.spec.ts` 时，用「对应 AC 编号」作为用例的标注（见 `product-e2e-test`）。

**产出后必做：盖章** —— 运行 `product-workflow/scripts/check_freshness.py --stamp <本文档路径>`，在文档**开头**写入「生成元信息」块。本模块文档**依赖两个上游**（产品设计文档 + 功能架构文档），所以块里会有两条指纹记录。**不要手工删改**——任一上游的契约变了（新增 AC、加表、加接口），本文档就会被判陈旧，`M1` 悬空检查也会同步报警。

## 4. 命名规范（硬约束）

| 对象 | 规范 | 示例 |
|---|---|---|
| 文档文件 | `<序号>_<模块名>详细设计.md` | `01_用户管理模块详细设计.md` |
| 页面 / 组件文件 | PascalCase | `UserManagement.tsx`、`ProjectList.tsx` |
| 样式文件 | kebab-case | `data-list-page.scss` |
| 工具函数 | camelCase | `dateUtils.ts` |
| TS 接口 | PascalCase，字段 camelCase | `interface Project { createdAt: string }` |
| 对外 API 字段 | camelCase | `excelFile`, `updatedAt` |
| DB 列 / 表 | snake_case | `created_at`, `project_management` |
| 后端（Python） | Pydantic / SQLAlchemy 蛇形 | `project_id` |

**技术栈基线**：前端 React 18 + TypeScript + Vite + Ant Design（主线）；状态管理 Zustand / Redux Toolkit；后端 FastAPI + SQLAlchemy + PostgreSQL。详见 `product-development`。

## 5. 自检清单

**先说清哪些是脚本查的、哪些靠人工**：

| 自检项 | 承担者 |
|---|---|
| 模块文档引用的 AC 在产品设计文档中存在（不悬空） | `M1`（脚本 FAIL） |
| 「本模块覆盖的 AC」与测试用例表引用的集合一致 | `M2`（脚本 FAIL） |
| 每个接口含 Endpoint / 请求参数 / 成功响应 / 错误响应 | `M3`（脚本 FAIL） |
| DDL 含 `CREATE TABLE` 且有索引声明 | `M4`（脚本 FAIL） |
| Mermaid 合规 | `M5`（脚本 FAIL） |
| DDL 有注释 / 覆盖清单内编号不重复 | `M6`（脚本 WARN） |
| API 契约与功能架构文档**逐字段**一致 | **人工**（endpoint 集合可比，字段级差异靠人核） |
| 产品设计部分为**完整复制**、代码结构可追溯 | **人工**（无法判定"是否改写"） |
| 命名符合第 4 节 | **人工**（部分可落 eslint，但那属代码阶段） |

**自检清单**

- [ ] 产品设计部分为**完整复制**（无删减、无改写、格式原样）
- [ ] 前端代码结构 / 后端代码结构均可追溯到功能架构文档
- [ ] API 契约与功能架构文档**一致**（未新增、未改名、未改字段）
- [ ] 每个接口都有请求参数、成功响应、错误响应三块
- [ ] 每张表有 DDL 且字段含类型/约束/索引/注释
- [ ] ER 图与表定义一致
- [ ] 命名全部符合第 4 节（重点核对 camelCase / snake_case 不混用）
- [ ] 已列出**本模块覆盖的 AC 编号**，且与产品设计文档的「验收标准」逐条对得上（不多、不少、不改号）
- [ ] 测试用例表的「对应 AC 编号」列已填，且本模块每条 AC 至少被一条用例覆盖
- [ ] 测试用例覆盖该模块的每个 API 与每条主要交互
- [ ] 所有 Mermaid 图遵守 `product-workflow/references/mermaid-guide.md`
- [ ] 运行 `scripts/validate_module_doc.py` 判定 PASS

```bash
python3 scripts/validate_module_doc.py \
  --module-doc <项目根>/项目战术执行/<序号>_<模块名>详细设计.md \
  --design-doc <项目根>/项目战术执行/00_产品设计文档.md
```

> `M1` 悬空检查与 `M2` 一致性检查**必须传 `--design-doc`** 才有意义 —— 它们防的正是「上游改了、模块文档没同步」这类**静默漂移**：没有外部症状，只能靠脚本发现。

## 7. 常见失败模式

| 症状 | 原因 | 应对 |
|---|---|---|
| 文档很长但开发者仍要翻产品设计文档 | 「产品设计」部分做了概述而非完整复制 | 改为原文完整复制 |
| 代码写完发现接口对不上 | 详细设计里自行改了 API 字段 | 回到功能架构对齐，禁止擅自改契约 |
| camelCase / snake_case 混用 | 未按第 4 节分层（API 层 vs DB 层） | 明确：**对外 API 一律 camelCase，DB 一律 snake_case**，转换在后端序列化层 |
| 测试用例写了但跑不起来 | 缺前置条件与环境准备描述 | 补齐「前置条件」列与 E2E 环境准备伪代码 |
| 设计做完了，E2E 却不知道测什么 | 模块设计没有承接 AC，测试用例凭感觉写 | 在「本模块覆盖的 AC」里显式列出编号，测试用例表补「对应 AC 编号」列 |
| 模块设计里的 AC 编号和设计文档对不上 | 手抄编号出错，或上游改了没同步 | 编号一律从产品设计文档复制，禁止手打；对不上时回流上游确认 |
