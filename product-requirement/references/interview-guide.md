# 访谈问题清单（七类）

> 用法：访谈前过一遍，勾出本次适用的问题；材料里已有答案的不要问。追问到「可验收」为止。
> 一次问一类，按序推进——先背景后细节，避免上来就抠字段。

## 1. 业务背景与目标

- 这件事要解决的**业务问题**是什么？（不是"要做一个功能"，而是"现在哪件事做不了/做不好"）
- 做成后的**成功标准**是什么？（谁来评判、看什么数字）
- 为什么是现在做？（触发事件 / 上级要求 / 竞品压力）
- 有没有**不做**的替代方案？（有时答案是流程调整而非系统）

⚠️ 常见坑：用户直接跳到「我要一个 XX 页面」。先拉回问题层——页面只是他设想的一种解。

## 2. 用户与场景

- **谁**用？（角色、频次——每天用还是每月一次）
- 在**什么场景**下用？（桌面/手机、独立操作还是边打电话边操作）
- 一次典型使用从哪开始、到哪结束？（走一遍主流程）
- 有没有**不用**这个系统的人会被影响？（被录入数据的一线、被报表考核的团队）

## 3. 范围与优先级

- 这次**必须做**的是什么？（MoSCoW：必须有 / 应该有 / 可以有 / 暂不做）
- 明确**不做什么**？（写进基线，防范围蔓延——比写"做什么"更重要）
- 有没有"顺手做一下"的隐性期待？逐条摆到台面上定性。
- 分期计划？一期边界在哪？

## 4. 数据与口径（数据/指标类需求必问）

- 每个指标/状态的**精确定义**：公式、枚举值、边界值。
  - 例：「活跃用户」＝?（登录过？产生行为？时间窗多久？去重口径？）
- 数据**从哪来**：人工录入 / 系统同步 / 导入？源头系统的字段可信吗？
- **历史数据**要不要迁移、清洗？
- 汇总口径：时间维度（自然日/工作日/时区）、组织维度（按人/按部门/含子部门）？
- 权限口径：谁能看谁的数据？（行级 / 列级 / 角色）

⚠️ 常见坑：「大概」「差不多」「跟 XX 系统一样」都不算澄清完成——拿到公式或枚举才算。

## 5. 验收标准

- 每条主要需求：**做完怎么算对**？（用用户的语言写一句可判定的验收描述——它是后续 AC 编号的原料）
- 异常与边界：没数据时显示什么？并发冲突？超长输入？
- 性能/量级预期：数据量多大、多少人同时用？（影响技术方案，先记下即可，不用深挖）

## 6. 约束与依赖

- 技术约束：指定技术栈？必须部署在哪？对接哪些现有系统（接口谁开）？
- 合规/安全约束：数据能不能出内网？留痕要求？
- 时间与资源约束：deadline 是硬的软的？谁来配合（甲方接口人）？
- 流程约束：上线要不要培训、试运行、审批？

## 7. 交付范围（必问——决定链路走多远）

- 本次要交付到哪一层？三选一，与用户明确说出选项：
  - **产品设计** —— 只做需求澄清与产品设计文档，不含架构与代码
  - **设计到模块** —— 到全部设计文档（含架构、模块详细设计），不写代码
  - **全链** —— 设计 → 开发 → E2E 测试 → 结项
- 确认结果写进基线顶部：`交付范围：<档位>`（编排器按此裁剪结项判定）。

## 追问技巧

- **先检查前提再追问**：用户的需求表述常带隐含假设（"要导出"隐含数据已在系统里、"要像 XX 那样"隐含那个系统的业务前提成立）。先摆出假设验证（「这里默认了数据已经在库里，对吗？」），前提不成立就直接说——**不要在错误前提上继续收集细节**。
- **追问到例证**：「能不能给一个真实例子的完整流程？」——故事比抽象描述暴露的需求多。
- **反向确认**：「我理解你**不是**要 X，**而是** Y，对吗？」——用否定句验边界。
- **两难显性化**：两个诉求冲突时摆出「A 则 B 不可得」让用户选，不要和稀泥；用户的说法与他自己前面定的目标矛盾时，直接指出来（不附和），让矛盾在访谈里解决而不是流进基线。
- **沉默三秒**：用户答完后停顿，常会自己补出关键约束。
- **每次访谈收尾**：口头复述本次确认的结论清单 + 遗留问题，当场纠偏；归纳出的结论标注【推测】请用户确认，确认后才升级为【事实】。
