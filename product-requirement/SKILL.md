# 需求沟通与澄清（阶段⓪ · 链路入口）

> 定位：链路的「问清楚」环节。**产出物不是设计，而是一份让用户拍板的《需求澄清报告》。**
> **硬约束：用户未确认前，不得启动阶段 ①（产品设计）。** 确认是用户行为，任何脚本与 AI 判断都不能代替。

项目路径与技术栈优先读取项目根 `product-workflow.json`；下文路径为默认示例，详见 `product-workflow/references/project-config.md`。

## 1. 触发门槛（先过这一关，再进入访谈）

**本 skill 是整条交付链的入口——触发它就意味着一条可能很长的链路要启动。宁缺勿滥。**

### 1.1 进入条件（实质判断，不是关键词匹配）

同时满足才进入：

1. **有真实交付意图** —— 用户要的是"做出一个东西/系统/功能"，而不是了解、咨询、评估
2. **需求存在实质缺口** —— 至少一项：目标不可验收、范围边界不清、口径无法判定、干系人有分歧、**没有书面且经用户认可的需求文档**

### 1.2 不触发清单（命中任意一条 → 不进入本阶段）

- 简单问答 / 咨询可行性（"能不能做 X"）—— 直接回答，不启动访谈
- 用户已给出完整书面需求且明确认可 —— 直接送 `product-design`
- 单点小改动 / 一个明确的小任务 —— 直接执行，不需要澄清报告
- 用户只是想看看模板、了解流程 —— 给材料，不建项目
- 对话中的随口提及（"以后要不要做个 XX"）—— 不当成启动信号

### 1.3 拿不准时

**先问一句再动**：「这看起来要启动完整的交付链（需求澄清 → 设计 → …），你是想现在正式立项，还是先随便聊聊？」——用户确认立项才进入本阶段。**不要因为命中了触发词就自作主张开访谈。**

触发词（需求访谈、澄清需求、对齐口径…）只是**检索线索**，生效前提是 1.1 的两个条件成立。

## 2. 回答原则（本阶段对用户的每一次发言都适用）

> 这四条不是客套话，是访谈质量的地基。每一条都落到具体动作：

1. **先检查前提** —— 用户提出的需求本身常带隐含假设（「我需要一个导出功能」隐含"数据已经在系统里"、"导出格式已想好"）。**先摆出假设并验证，再顺着需求往下走**；前提不成立时直接说，不要在错误前提上展开访谈。
2. **独立判断，不附和** —— 用户的说法与证据、目标冲突时直接指出（「这个诉求和你在第 3 条说的成功标准是矛盾的」）。访谈的产出是**澄清后的真需求**，不是用户原话的复读；讨好式附和会把这些矛盾原样带进基线，在下游放大。
3. **标注来源** —— 报告与对话中区分三类：**【事实】**（用户原话/已有材料）、**【推测】**（AI 归纳但未经确认）、**【观点】**（AI 建议，供决策）。未确认的归纳不得写成事实——澄清报告里每个关键结论都带标注，用户确认时才知道哪些是自己说过的、哪些是 AI 替他想的。
4. **主动提醒** —— 用户没提但会影响成败的变量要主动摆出来：被忽略的数据（历史数据、权限、运维成本）、隐性代价（口径后续变更会波及链路全部下游）、常见认知偏差（锚定在用户设想的第一个方案上、沉没成本驱动范围扩张）。提醒一次即可，由用户决定是否纳入——**提醒不等于替用户扩范围**。

## 3. 与阶段①「需求说明」的边界（不是同一件事做两遍）

| | ⓪ 本 skill | ① product-design 的需求说明 |
|---|---|---|
| 时机 | 确认**前**，与用户对话 | 确认**后**，落笔成文 |
| 输入 | 用户的口头描述、零散材料 | 已确认的 `原始需求.md` |
| 动作 | 提问、澄清、记录分歧、请用户拍板 | 把基线结构化（概要/入口/页面描述/功能说明） |
| 产出 | 《需求澄清报告》+ 已确认基线 | 产品设计文档的前置章节 |

## 4. 工作流程（五步，顺序不可颠倒）

| 步 | 动作 | 要点 |
|---|---|---|
| 1 | **访谈准备** | 按 `references/interview-guide.md` 列问题清单；先读用户已有材料（文档、截图、竞品），别问材料里已有的答案 |
| 2 | **访谈与追问** | 一次问一类（背景 → 用户场景 → 范围 → 口径 → 验收 → 约束 → 交付范围）；追问到「可验收」为止：**每条需求都能回答"做完怎么算对"**；全程遵守第 2 节回答原则 |
| 3 | **澄清收敛** | 把回答整理进报告（带来源标注）；**分歧不当场裁决**，列进「分歧与待确认项」并给选项；口径类澄清必须落到可判定的定义（公式、枚举、边界值） |
| 4 | **产出报告** | 按 `references/clarification-report-template.md` 生成《需求澄清报告》落 `项目战略规划/需求澄清报告.md`；「需求基线」章节写成**可直接誊写**的干净需求（不要混入 Q&A） |
| 5 | **用户确认与移交** | 把报告交用户逐节确认，**产出报告后显式停下等确认，不要自己往下走**；确认后：① 报告头部确认状态改「已确认（日期）」；② 把「需求基线」章节誊写为 `项目战略规划/原始需求.md`（**顶部带交付范围声明**——它在访谈中确认）；③ 此后才能调用 `product-design` |

**交付范围必须在访谈中确认**（`产品设计` / `设计到模块` / `全链`）——它决定后续链路走多远，属于需求的一部分，不要留给用户事后补。

## 5. 产物

| 产物 | 路径 | 说明 |
|---|---|---|
| 需求澄清报告 | `项目战略规划/需求澄清报告.md` | 过程资产：访谈记录、澄清决策、分歧与待确认项、确认状态 |
| 需求基线 | `项目战略规划/原始需求.md` | 确认后从报告「需求基线」章节誊写；链路唯一输入；**不再追加过程信息** |

**报告与基线分开的理由**：报告回答「我们怎么问清楚的」（审计与回溯用），基线回答「确认要做的是什么」（链路消费）。混在一个文件里，下游会引用到未确认的 Q&A 内容。

## 6. 硬规则

1. **确认门禁是人工门禁** —— 报告确认状态为「已确认」之前，禁止把需求基线写入 `原始需求.md`，禁止建议用户启动阶段 ①。
2. **分歧不裁决，只记录** —— 澄清报告列「分歧 + 各方立场 + 建议选项」，由用户选；AI 不得替用户拍板业务决策。
3. **口径必须落到可判定定义** —— 指标/状态/枚举类回答必须追问到公式、枚举值或边界值；「大概」「差不多」不算澄清完成。
4. **基线誊写不得增删** —— 基线章节与 `原始需求.md` 内容一致；誊写时发现要改，回到用户重新确认那一节，不要悄悄改。
5. **来源标注不得省略** —— 报告中的关键结论区分【事实】/【推测】/【观点】；未确认的推测进入基线前必须先经用户确认升级为事实。
6. **表达遵守** `references/expression-principles.md`（结论先行、三步说清）——对用户的每一轮澄清汇报都适用。

## 7. 自检清单

- [ ] 已过触发门槛（1.1 两个条件成立；拿不准时问过用户是否立项）
- [ ] 每条需求都能回答「做完怎么算对」（可验收）
- [ ] 数据/指标类需求都有可判定口径（公式 / 枚举 / 边界值）
- [ ] 用户提出的隐含假设已摆出并验证；与目标冲突处已直说（未附和）
- [ ] 报告关键结论带【事实】/【推测】/【观点】标注；推测已全部经用户确认或仍在待确认项
- [ ] 分歧全部记录在「分歧与待确认项」，且带选项，没有 AI 代拍板
- [ ] 交付范围已与用户确认
- [ ] 报告确认状态已由用户置为「已确认」，基线已誊写为 `原始需求.md`
- [ ] `原始需求.md` 与报告「需求基线」章节逐字一致

## 可验证的确认记录

已有用户明确确认时直接沿用，不重复提问。将真实确认人、时间、确认位置及原始需求 SHA256 记入 `.product-workflow/approval.json`；字段见 `product-workflow/references/verification-contract.md`。记录版本绑定不替代真实人工确认，不得由模型补造。
