# E2E 功能测试

> 定位：**真实浏览器里跑通业务链路**，并在三个层面验证结果。
> 产物落目标工程的 `frontend/tests/e2e/<page-name>.spec.ts`（Playwright 必须在被测前端工程内才能运行）。

## 1. 何时使用

- 用户要写 E2E / 端到端 / Playwright 测试用例。
- 用户要为新页面或新功能补回归测试。
- 用户要排查 E2E 用例失败、不稳定（flaky）的原因。
- 模块详细设计文档里已有测试用例表，需要落成可执行脚本。
- 用户要检查「设计文档里的验收标准（AC）是否都被测到了」。

## 2. 用例与 AC 的对应（追溯锚点）

产品设计文档里每个页面/弹窗都有「验收标准」小节，条目形如 `AC-USER-01`（编号规则见 `product-design/references/product-design-spec.md` 第 6 节）。**每条用例都要标注它验证的是哪条 AC。**

```typescript
// AC-USER-03 删除需二次确认，确认后该行从列表移除
test('AC-USER-03 删除用户：二次确认后该行消失', async ({ page }) => {
  // ...
});
```

**硬要求**
- 注释格式 `// AC-<模块缩写>-<两位序号>`，后接该条 AC 的原文或摘要
- 用例名以 AC 编号开头 —— 失败时能直接定位到设计文档的哪一条
- 一条 AC 可以对应多条用例（正向 + 异常），但**每条 AC 至少由一项实际通过的单元/API/E2E 测试承接**
- 引用的编号必须真实存在，不能凭印象编

**双向检查** —— `scripts/validate_e2e_spec.py` 同时查两个方向：
- **静态 E2E 未引用**：提示 WARN；实际覆盖由结项器读取单元/API/E2E 执行报告，未覆盖则阻断
- **悬空**：用例引用了文档里不存在的 AC 编号 → FAIL

```bash
python3 scripts/validate_e2e_spec.py \
  --design-doc <项目根>/项目战术执行/00_产品设计文档.md \
  --spec-dir  <项目根>/frontend/tests/e2e
```

## 3. 核心设计：三层监控

E2E 的价值不止"点通"，而在于**捕捉静默失败**。测试全程挂三层监控：

| 层 | 监控什么 | 为什么必须 |
|---|---|---|
| 控制台日志 | `console.error` / `console.warn` | React 报错、AntD 警告、未捕获异常常不影响断言但已出错 |
| 网络请求 | 请求 URL / 方法 / 载荷 / 响应状态 | 接口 4xx/5xx 时前端可能"看起来正常" |
| 页面错误 | `pageerror` 事件 | 未处理的 Promise rejection、渲染崩溃 |

**原则**：即使断言全过，只要三层监控里有异常，测试就应当被标记为需要关注——**这往往是线上事故的前兆**。

## 4. 测试步骤执行标准

- **步骤分层 + 日志输出**：每一步 `console.log` 分隔并编号，失败时能立刻定位在哪一步。
- **等待策略**：优先用**状态等待**（元素可见/网络空闲/文本出现），不用固定 `waitForTimeout`。固定等待是 flaky 的头号来源。
- **元素定位**：使用**多兜底选择器**——依次尝试 `data-testid` → 语义角色（role + name）→ 文案 → CSS。单一选择器一旦文案微调就挂。

## 5. 用户交互模拟

- **表单填写**：填值前先校验当前值（避免重复填充或覆盖用户数据）；下拉/日期选择器有独立处理方式。
- **复杂交互**：动态列表（增删行）**从后往前删**（避免索引偏移）；多步流程逐步校验再进入下一步。

## 6. 数据验证方法（三层）

| 层 | 手段 | 适用于 |
|---|---|---|
| 前端 | 元素可见性、文本内容、表格行数、状态标签 | 用户可见的界面结果 |
| API | 拦截请求，校验状态码与响应体字段 | 确认数据真的提交成功，而非前端假成功 |
| DB | 直连数据库断言记录 | 确认落库正确（字段值、软删标记、审计字段） |

**推荐组合**：一次写操作至少验「前端 + API」两层；涉及资金、权限、状态流转等关键链路必须三层全验。

## 7. 错误处理策略

- **异常捕获**：用例主体包 `try/catch`，catch 中输出当前步骤、三层监控快照、截图。
- **重试机制**：仅对已知不稳定的等待点做有限次重试，**不要用重试掩盖真实缺陷**。
- **兜底处理**：清理动作（关闭弹窗、清空数据）放在 finally，避免污染后续用例。

## 8. 可复用模板

`assets/templates/sample.spec.ts` —— Playwright + TS 用例骨架，三层监控、步骤分层、多兜底选择器、三层验证、AC 标注均已内置。

**复制后必须替换**：`BASE_URL`、菜单/按钮文案、元素选择器、API 路径、数据库断言。模板中 `setupMonitoring` 等必填函数默认抛出“尚未实现”，必须补全后才能通过；完整参考页面测试见 `product-development/assets/reference-app/tests/`。

## 9. 完成前自检清单

- [ ] 用例覆盖设计文档测试用例表中的每个 E2E 场景
- [ ] **在实际测试名称中标注 AC 编号，或通过 ac_tests 映射实际 JUnit 测试身份**
- [ ] **每条 AC 有实际通过的单元/API/E2E 测试承接**；静态引用检查不能替代执行报告
- [ ] 三层监控已挂载，且测试结束有汇总输出
- [ ] 无固定 `waitForTimeout`，全部改为状态等待
- [ ] 关键元素使用多兜底选择器
- [ ] 关键链路做了三层验证（前端 + API + DB）
- [ ] 失败路径（错误提示、权限拒绝）有用例覆盖
- [ ] 用例可独立运行，不依赖执行顺序
- [ ] 清理逻辑在 finally 中
- [ ] 报告输出包含：通过/失败数、失败步骤、控制台异常、失败请求

## 运行证据

按 `product-workflow/references/verification-contract.md` 配置 JUnit 报告并通过 run_checks.py 执行。报告必须来自本次运行；无测试、全部跳过、失败或陈旧证据不通过。AC 适合由单元或 API 测试验证时，不要求重复编写 E2E。
