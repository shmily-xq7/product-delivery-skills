# 产品交付全流程编排

> 定位：**流程大脑**。定义「在哪、产出什么、谁来做、什么时候算过」，并把具体产出交给各阶段 skill。
> 本 skill **不写设计文档正文**——只编排、路由、校验产物契约。

## 1. 何时使用

- 启动一个新的产品/功能设计项目，需要知道**从哪开始、按什么顺序推进**。
- 用户问「下一步该做什么」「这个产物放哪」「该参考哪份规范」。
- 需要判断某个阶段**是否通过门禁**，或不过门禁后该怎么回流。
- 需要向他人（或自己）交代**整条链路的环节与产物清单**。

若用户明确只要某一个阶段的产物（例如"写某页面的详细设计"），**直接路由到对应阶段 skill**，不必走本 skill。

## 2. 端到端链路

```
需求沟通⓪（访谈/澄清/用户确认）
   │  产出《需求澄清报告》→ 用户确认 → 确认基线誊为 原始需求.md
   ▼
原始需求 ──①──▶ 产品设计文档 ──②──▶ 功能架构设计文档 ──③──▶ 模块详细设计
                                                              │
                                                              ▼
                                                    ④ 代码开发 ──⑤──▶ E2E 测试 ──⑦──▶ 99_交付清单
                                                              │
                     任一环节卡住 ──⑥ 诊断──▶ 诊断报告 ──▶ 回对应阶段

横向支撑（任一阶段可调用）：
  产品视觉口径 product-ui-spec   ·   线框/原型 product-prototype   ·   格式转换 product-doc-convert
```

| 序号 | 阶段 | 承担 skill | 核心产出 |
|---|---|---|---|
| ⓪ | 需求沟通与澄清（用户确认门禁） | `product-requirement` | `项目战略规划/需求澄清报告.md` + 确认后的 `原始需求.md` |
| ① | 产品设计 | `product-design` | 产品设计文档 |
| ② | 功能架构设计 | `product-architecture` | 功能架构设计文档 |
| ③ | 模块详细设计 | `product-module-design` | 按模块的详细设计文档 |
| ④ | 代码开发 | `product-development` | 前端页面/组件 + 后端接口 |
| ⑤ | E2E 测试 | `product-e2e-test` | Playwright 测试用例 |
| ⑥ | 诊断（按需） | `product-diagnosis` | `项目战术执行/90_诊断报告_<主题>.md`（只读角色，不改既有文件） |
| ⑦ | 结项（按交付范围检查） | `product-workflow` | `项目战术执行/99_交付清单.md`（门禁结果 + AC 覆盖汇总 + 遗留项） |

**贯穿全链的锚点：AC 编号。** 阶段① 为每个页面/弹窗/步骤/tab 定义验收标准 `AC-<模块缩写>-<两位序号>`（如 `AC-USER-01`）；阶段③ 的模块详细设计列出「本模块覆盖的 AC」；阶段⑤ 每条用例在注释里标注它验证的 AC。于是「设计 → 模块 → 测试」三段可以对账，而不是各说各话。编号规则见 `product-design/references/product-design-spec.md` 第 6 节。

## 3. 产物目录与命名约定

**设计文档**统一落 `<项目根>/项目战术执行/`；**代码**落目标工程的 `frontend/`、`backend/`（完整约定见 `product-development` 的「技术栈基线」）。

```
<项目根>/
├── 项目战略规划/                           ← 需求侧（⓪ 产出 + 链路输入）
│   ├── 需求澄清报告.md                     ← ⓪ 产出（访谈记录 / 澄清决策 / 确认状态）
│   └── 原始需求.md                         ← 用户确认后的需求基线（① 的输入）
├── 项目战术执行/                           ← 只放设计文档
│   ├── 00_产品设计文档.md                  ← 阶段①产出（含前置章节：需求说明 / 设计初始化 / 功能清单）
│   ├── 00_功能架构设计文档.md              ← ② 产出
│   ├── <序号>_<模块名>详细设计.md           ← ③ 产出，如 01_用户管理模块详细设计.md
│   └── 90_诊断报告_<主题>.md                ← ⑥ 产出（按需；90_ 前缀排在模块文档之后）
│   └── 99_交付清单.md                       ← ⑦ 产出（终点；由 --finalize 生成）
├── frontend/
│   ├── src/views/<ModuleName>/            ← ④ 前端产出（组件/页面文件 PascalCase）
│   └── tests/e2e/<page-name>.spec.ts      ← ⑤ 产出（kebab-case）
└── backend/app/                           ← ④ 后端产出（api/v1、services、models、schemas）
```

**硬约定**
- **确认门禁（人工，链路入口）**：`原始需求.md` 必须来自**用户已确认**的《需求澄清报告》——报告头部的确认状态为「已确认」后，才把报告中的「需求基线」章节誊写为 `原始需求.md`。确认是用户行为，**无脚本可代替**；不要在报告未确认时启动阶段 ①。
- **阶段① 的三个子阶段（①需求说明 / ②设计初始化 / ③功能清单拆解）不单独建文件** —— 它们的产出并进 `00_产品设计文档.md` 的**前置章节**。这三章**按需出现**（材料不齐可整章省略），**无门禁校验**；校验脚本只检查主体章节（业务流程 / 页面清单 / 功能设计详情）。
- **产物编号约定**：`00_` 全局文档（产品设计 / 功能架构）｜`01_`… 模块详细设计（两位序号，排序稳定）｜`90_` 诊断报告｜`99_` 交付清单（终点）。
- 模块详细设计文件名必须是 `<序号>_<模块名>详细设计.md`。
- **诊断报告**落 `项目战术执行/90_诊断报告_<主题>.md`；用 `90_` 前缀排在模块文档之后。同一问题反复诊断**追加到同一文件**，不要建一堆 `90_` 文件。
- **交付清单**落 `项目战术执行/99_交付清单.md`，由脚本生成、**请勿手工修改**（改过的清单不再可信）；上游变更后重跑 `--finalize` 刷新即可。
- **交付范围声明**（部分交付）：在 `原始需求.md` 顶部写一行 `交付范围：仅需求分析`（或 `设计到模块` / `全链`，**缺省全链**）。结项按声明裁剪——范围外阶段标「不在本次交付范围」、不计入就绪；范围外**产物若存在**会提示「超出范围」（不阻断，但提示核对声明是否过期）。**体检（陈旧检测）不受范围影响**：改了上游，范围外的下游照样告警。
- `项目战略规划/` 与 `项目战术执行/` 两个目录名固定，**不要另起名字**——各阶段 skill 的产物约定与命令都按此路径书写。注：**校验脚本本身不依赖目录名**，它接受任意 `--doc` / `--spec-dir` 路径，只是流程中的调用示例按此约定书写。
- **代码产物落目标工程**（`frontend/`、`backend/`），**不落** `项目战术执行/`。
- **每份设计类产物产出后必须盖章** —— 运行 `scripts/check_freshness.py --stamp <产物路径>` 写入「来源指纹」，否则无法判定它是否陈旧（协议见第 5 节）。

## 4. 阶段输入 / 输出契约

| 阶段 skill | 输入 | 输出 | 门禁（不通过即回流） |
|---|---|---|---|
| `product-requirement` | 用户口头需求 + 已有材料 | `项目战略规划/需求澄清报告.md` + 确认后誊写 `原始需求.md` | **人工确认门禁**：报告确认状态 =「已确认」（用户行为，无脚本）；基线誊写与报告第 8 章逐字一致 |---|
| `product-design` | `项目战略规划/原始需求.md` | `项目战术执行/00_产品设计文档.md` | 文档含规定章节（业务流程 / 页面清单 / 功能设计详情）+ 实际 Mermaid 图 + 每页/弹窗 ≤2 张表 + **AC 编号格式合法且全文唯一、每个页面至少 1 条**；`product-design/scripts/validate_design_doc.py` 判 PASS（C1–C15）。**注：`字段规格只在一处出现` 是人工核对项；前置章节（需求说明/设计初始化/功能清单）按需出现，不校验** |
| `product-architecture` | `00_产品设计文档.md` | `00_功能架构设计文档.md` | 实际 Mermaid 图 + Mermaid 合规（无全角 / 不用 `flowchart` / 子图不用 `direction`）+ 每张表有字段定义表（列头含 字段名·类型·约束·描述）与表级「索引」行 + 组件树命名 PascalCase；`product-architecture/scripts/validate_arch_doc.py` 判 PASS（A1–A6）。**注：「全功能被覆盖」「API/DB 命名分区」属弱检查（WARN），判断类内容靠人工** |
| `product-module-design` | 上两者 | `<序号>_<模块名>详细设计.md` | **AC 不悬空，且「本模块覆盖的 AC」与测试用例表引用一致** + 每个接口含 Endpoint/请求参数/成功响应/错误响应 + DDL 含 `CREATE TABLE` 与索引声明 + Mermaid 合规；`product-module-design/scripts/validate_module_doc.py` 判 PASS（M1–M6）。**注：API 契约逐字段与架构一致、产品设计部分完整复制为人工项** |
| `product-development` | 模块详细设计 | `frontend/src/views/**` + `backend/app/**` | **跑项目自身工具链，不另造检查器**：`tsc --noEmit` 零错误 + `eslint --max-warnings 0` + `pytest` / `playwright test`；命名基线与无硬编码枚举落到 eslint 规则。详见 `product-development` 的「④ 阶段门禁」 |
| `product-e2e-test` | 代码 + 设计文档 | `frontend/tests/e2e/*.spec.ts` | 三层验证（前端 / API / DB）全绿；无 console 报错与失败请求；**每条 AC 至少被 1 个用例引用**（`product-e2e-test/scripts/validate_e2e_spec.py`） |
| `product-diagnosis` | 任一失败产物或报错 | `项目战术执行/90_诊断报告_<主题>.md`（含修复建议清单） | —（只读角色，不产出被下游消费的产物，不设门禁） |

## 5. 门禁与失败回流

**标准动作**：每个阶段产出后，先跑该阶段的「自检清单」，再进入下一阶段。

**回流路径**
```
任一阶段门禁不过
   ├─ 原因属于"本阶段产出质量问题" ──▶ 回到本阶段重做
   ├─ 原因属于"上游输入缺失/矛盾" ──▶ 回到上游对应阶段修正，再顺流而下
   └─ 原因无法定位 ─────────────────▶ product-diagnosis 出报告（落
                                      项目战术执行/90_诊断报告_<主题>.md）──▶ 再决定回流目标
```

**关键原则**
- **禁止跳阶段**：产品设计文档未过门禁，不要开始功能架构设计；架构未定，不要写模块详细设计。跳阶段的代价在下游成倍放大。
- **诊断只出报告不动手**：`product-diagnosis` **不改任何既有文件**，唯一写入是**新建** `90_诊断报告_<主题>.md`；修复动作回到对应阶段 skill 执行。

**陈旧检测：上游变更如何作废下游**

上面的回流只覆盖「门禁不过」。还有一种**更隐蔽**的失效：上游改了，下游产物还是按旧版做的——它不报错、不失败，只是**已经错了**。为此每份产物都要带一个「来源指纹」。

| 产物 | 记录谁的指纹 | 指纹方式 |
|---|---|---|
| `00_产品设计文档.md` | `项目战略规划/原始需求.md` | **整文件 sha256**（需求变本就该重审全链，这条边上"过度敏感"是对的） |
| `00_功能架构设计文档.md` | `00_产品设计文档.md` | **契约指纹** = {页面名集合, AC 编号集合} |
| `<序号>_<模块名>详细设计.md` | 产品设计文档 + 功能架构文档 | **契约指纹** = {AC, 表名, endpoint} |

**契约指纹只对「集合」取哈希**，所以**改一个错别字不会告警，而新增页面 / 改动 AC / 加表 / 加接口会** —— 灵敏度恰好等于"实质变更"，避免告警疲劳（一个老报假警的门禁，人会开始无视它）。

**代码与 E2E 用例不单独标记** —— 往源码里塞哈希会污染代码；它们由「最近的陈旧上游」**推导**：只要 ③ 陈旧了，④⑤ 自然该按序重跑。

**阶段产出后必须盖章**：

```bash
python3 product-workflow/scripts/check_freshness.py --stamp 项目战术执行/00_功能架构设计文档.md
```

**随时体检**（判定为陈旧 = 必须回流）：

```bash
python3 product-workflow/scripts/check_freshness.py --project-root <项目根>
```

输出会直接说明**变了什么**、**该从哪个阶段重跑**：

```
[STALE] 项目战术执行/01_用户管理模块详细设计.md 疑似陈旧（上游已变）
        上游变更：项目战术执行/00_产品设计文档.md
        指纹 fp:e43eb0b86205 -> fp:5c8e0653bd5e
        集合 AC 9 · 页面名 2 -> AC 10 · 页面名 2
        建议回流：product-module-design → product-development → product-e2e-test
```

> 两份文档的**元信息块格式**（写在文件开头，由脚本生成，勿手工改）：
>
> ```
> > **生成元信息**（由流程写入，请勿手工修改）
> > 基于：
> > - `项目战术执行/00_产品设计文档.md` @ `fp:e43eb0b86205`（AC 9 · 页面名 2）
> > 生成于：2026-09-10 17:41
> ```

**终点：交付清单（结项检查）**

链路的终点不是"E2E 跑绿了"，而是**一次结项检查通过**（按交付范围声明裁剪判定范围）：

```bash
python3 product-workflow/scripts/check_freshness.py --finalize --project-root <项目根>
```

它生成 `项目战术执行/99_交付清单.md`，把五件事一次性判定完：

| 结项条件 | 判据 |
|---|---|
| 产物齐全（按交付范围） | 全链：三类设计文档 + 代码目录；`设计到模块`：设计/架构/模块文档；`仅需求分析`：产品设计文档 |
| 来源链自洽 | 无陈旧、无未标记产物（对所有**存在**的产物判定，不受范围限制） |
| 各阶段门禁 PASS | **只跑交付范围内阶段**的校验器并汇总；范围外阶段标「不在本次交付范围」 |
| **AC 覆盖（按交付范围）** | 全链判三环（设计 N → 模块 M → 用例 K）；`设计到模块` 判两环；`仅需求分析` 不判（AC 格式与唯一性已由 ① 门禁 C12–C14 覆盖） |
| 无遗留未确认项 | 收集 `90_诊断报告_*.md` 的「未确认项」 |

> **部分交付**：只想做需求分析（或做到模块设计）时，在 `原始需求.md` 顶部声明 `交付范围`，结项只判范围内条件，**未声明默认全链**（老项目行为不变）。范围外产物若已存在，会在清单第 6 节提示「超出交付范围」。

**"项目交付完成"因此有了可判定的定义**：`99_交付清单.md` 存在且结论为**就绪**（退出码 0）。未就绪时退出码 1，并列出待处理项与重跑命令。

> **顺序提醒**：`--finalize` 依赖各产物的「生成元信息」块，所以每次阶段产出后先 `--stamp`，结项时才判定得准。

## 6. 路由表（触发词 → skill）

| 用户意图 / 触发词 | 路由目标 |
|---|---|
| 需求访谈、澄清需求、对齐口径、需求不清晰、需求调研、和用户确认需求 | `product-requirement`（**须有真实交付意图且需求有实质缺口**——触发门槛见其 §1，拿不准先问用户是否立项；命中触发词但无交付意图时不路由） |
| 写产品设计、写需求说明、设计初始化、拆功能清单、页面清单、字段字典、交互矩阵 | `product-design` |
| 定架构、技术选型、系统分层、功能架构设计文档、ER 图、接口契约（宏观） | `product-architecture` |
| 某模块详细设计、页面详细设计、接口契约（细化）、数据模型、DDL | `product-module-design` |
| 按设计写代码、生成页面组件、对接 API、列表页/标签页开发 | `product-development` |
| 写测试、E2E、集成测试用例、回归、Playwright | `product-e2e-test` |
| 为什么不过门禁、哪里不符合规范、帮我诊断、排查流程 | `product-diagnosis` |
| 项目能不能交付、结项、交付清单、做完了吗、还差什么 | 本 skill（`--finalize` 结项检查） |
| 只做需求分析、部分交付、只到设计不写代码、交付到哪一层 | 本 skill（`原始需求.md` 声明 `交付范围` + `--finalize`） |
| 上游改了、下游要不要重做、产物是不是陈旧 | 本 skill（`--project-root` 体检） |
| 设计后台界面、设计系统、双主题、配色 token、表格/弹窗规范 | `product-ui-spec` |
| 画 ASCII 线框、做静态 HTML 原型、复刻页面 | `product-prototype` |
| 文档转 md、表格做 docx、导出 excel | `product-doc-convert` |

## 7. 阶段边界（重要：避免职责重叠）

**常见陷阱**：产品设计与系统架构的职责极易互相侵入——两边都会不自觉地去拆模块、列页面清单，结果同一件事被写两遍且彼此矛盾。本族对此**强制划清**：

- **`product-design` 只做业务侧**：业务流程、页面清单、页面/弹窗的字段与交互、页面级数据流。**不涉及**技术选型、表结构 DDL、服务分层、组件树。
- **`product-architecture` 只做技术侧**：总体技术方案、服务/模块划分、表定义与 ER 图、前端组件树、API 命名规范。**不重复**描述页面字段的业务含义（引用产品设计文档即可）。
- 二者交汇点只有一处：**功能/模块清单**。以产品设计文档为准，架构文档不得新增或改名业务功能。

**⓪ 与 ① 的边界（需求沟通 vs 产品设计）**：

- **`product-requirement` 只管「把需求问清楚并让用户确认」**：访谈提问、澄清收敛、分歧与待确认项记录、交付范围确认、产出《需求澄清报告》与已确认的 `原始需求.md`。**不做**页面设计、不做技术方案、不定义 AC。
- **`product-design` 消费已确认的基线**：① 的前置子流程「需求说明」是把确认后的需求**落成结构化描述**（它的输入是 `原始需求.md`），而 ⓪ 是「让这份基线诞生并被确认」。一个是确认前与用户对话，一个是确认后落笔成文——**不是同一件事做两遍**。
